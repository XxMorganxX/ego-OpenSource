# Spec: SKU history audit trail

Proposal from [[Sam Rivera]]: every SKU mutation in the fruit-inventory service should write an append-only audit row so [[Avery Quinn]]'s team can reconstruct inventory state at any past timestamp.

## Problem

Today a SKU row is updated in place. When a count changes, the old value is gone. After the [[2026-01-22 dup sku bug|duplicate SKU bug]] we could not say exactly what the stock report showed at 07:00 that morning, only what it showed after the cleanup.

## Proposal

- A new audit table with one row per change: SKU id, batch id, field, old value, new value, who or what made the change, and when.
- Rows are only ever inserted. No updates, no deletes.
- A function that rebuilds the state of any SKU at a given timestamp by replaying its audit rows.

## Costs

- Roughly one extra row per import line. At current volume that is small.
- Every code path that changes a SKU must go through one function, so nothing can skip the audit row.

## Open questions

- How long to keep audit rows. Sam suggests forever; Avery wants a number before approving.
- Whether cold-storage temperature readings belong in the same table. Sam says no: they are readings, not changes.

Background reading: [[Learning - Append-only audit trails]]. Decision pending.
